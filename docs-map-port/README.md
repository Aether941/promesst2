## 1. 定位与总原则

原生 JS + Canvas 单页;规则逐函数移植;**视野整幅大地图**;撤销为**无上限差分历史且跨会话完整持久化(IndexedDB)**;界面层 HTML。规则照抄、渲染尽量还原、网页层自由。

## 2. 范围与保真边界

### 2.1 必做

- 完整世界:两层 24×24(4×4 房间 × 6×6),环形卷绕;
- **整图视野**:当前层全幅;缩放 1–4×、可跟随玩家;“查看另一层”为视角装饰;
- 玩家移动 + 5 色能力(红开门/绿穿墙/黄碎石/橙双步/紫远行);
- X 键功能=拾/放宝石(原 Z 键移位?注:拾/放宝石=原 X 功能,现由 **V** 承担);供电;Z=撤销;
- 光束与 Z→X 的“射击”移位语义不变:行动照抄 `move/drop/shoot`;
- Rover 自主运行(全图 1 只,照规则);
- **逐步一次性撤销(无上限)**、checkpoint(拾魔杖生成、菜单恢复);
- IndexedDB 存/读档(含完整历史)、通关动画与 USED n ZAPS;
- 菜单:继续 / 从 wand 恢复 / 新游戏 / Credits / 存盘退出。

### 2.2 不做

- 重做(裁定 2);`magic` 房间旋转;被裁 `shoot()`;`push_rovers`;触屏;声音;反射镜 HUD(无来源)。

## 6. 关键技术决策

### 6.1 主循环

同 v3:rAF → 16ms 步进;超 250ms 复位;按键排队(仅 `player_timer<=0 && shot_timer<=0` 时消费,复刻每 80ms 一步、不吞键);插值照抄。

### 6.2 输入(裁定 3/5)

| 动作 | 键 | 说明 |
|---|---|---|
| 移动 | 方向键 / WASD | 原规则 |
| **撤销上一步** | **Z** | 原版为 Backspace,网页版统一用 Z(Backspace 不作别名,避免误触) |
| **射击(魔杖重定向)** | **X** | 原版 Z 的职责 |
| **宝石拾取/放置** | **V** | 原版 X 的职责 |
| 反射镜(逻辑保留) | C | 无 HUD 提示(关卡无 `/` 来源) |
| 菜单 | Esc | 即暂停 |
| 调试(可选) | 隐藏面板开关 | g/n 收进调试面板 |

HUD 提示文案随键位更新(例:`X TO FIRE / V TO GET/PUT / Z TO UNDO`)。

### 6.3 渲染与整图取景(裁定 1)

同 v3:整幅当前层、等比适配、1–4× 缩放、可跟随;“查看另一层”只切视角不改 `pz`。

### 6.4 动作模型

1. 若操作将改变世界:先按“当前状态 vs 最近提交点”生成差分条目(§6.6)再执行;
2. 判定顺序照抄 `move()` L742–853(去掉跨房打点/seen);
3. 结算重算供电/光照;rover 自主步进自然落入下次提交差分。

**紫光远行(必须照抄 C,勿加“遇墙即停”)——L753–770 与 L787–801 的分工:**

| 阶段 | 原版行为 | 实现要求 |
|---|---|---|
| 触发 | `light_for_dir[py][px][proposed_pdir] == POWER_travel \|\| [proposed_pdir^2] == POWER_travel` | 起点四向里“按键方向或其反向”有紫光 |
| 滑行 | `while (该格 proposed/^2 仍为紫光) 前进` | **只看紫光,不判墙/投影器/反射镜**——光束本身穿墙(§7 B),所以滑行会跨过墙格 |
| 收尾 | 退一格 → 若仍在原地则 `travel=0`(退化为普通移动) | 落点=“最后一格仍在紫光上”的格子 |
| 落点判定 | L787–801:先判“当前站在墙内无绿光→返回”;再判落点:墙无绿光→返回;门需红光;石块需黄光;投影器/反射镜不可站 | **落点是墙且无绿光 → 整个动作失败(人不动)**;有绿光时允许(绿光本就能站在墙里) |

> 教训 1:早前在滑行里加“遇墙即停”属自创规则,会让 224 个远行情景中 202 个结果错误(墙上投影器/穿墙光路被截断)。已回退为原版逻辑。
>
> 教训 2(坐标参数顺序):本工程里 `world.tile[z][行][列]`、`light_for_dir[行][列]` 是 **行在前**,而 `cellKind(z, 列, 行, …)`、`glideTarget(z, 列, 行, …)`、`roverCanEnter(z, 列, 行, …)` 是 **列在前**。任何一处传反都会“静默失败”(查到了转置后的另一格)。已发生的两次事故都源于此:`isTravelCell(行,列)` 与 `cellKind(z, gy, gx)`。新增此类函数时请显式标注参数含义,并在调试行确认“落点瓦片/判定”。

**橙光双步(必须照抄 C,勿加“中途拦截”)——L772–801 只判“终点”那一格:**

| 阶段 | 原版行为 | 实现要求 |
|---|---|---|
| 步长 | `x *= (1 << abilities[POWER_double])` | 步长 = 2^橙光数,即 2 格 / 4 格 … |
| 终点 | `gx = WRAP_X(px+x); gy = WRAP_Y(py+y)` | 一次算到终点,**只对终点做判定** |
| 中途格 | C 中完全不访问中途坐标 | **一律越过**:中途是墙/门/石块/投影器/反射镜都不判定(不开门、不碎石、不需要绿光) |
| 终点判定 | L787–801 | 墙需绿光;门需红光(开门且**不前进**);石块需黄光(碎石且**不前进**);投影器/反射镜不可站 |
| 结论 | — | “没有红光也能用橙光跳过一格门”是**原版行为**;只有终点是门时才会被挡/开门 |

> 教训 3:本项目曾在 v0.6.0–v0.6.2 期间按早期反馈加了“双步中途门/石拦截”,属自创规则(会让橙光在门/石旁边无法前进)。v0.6.3 已回退为只判终点。

### 6.5 Rover

同 v3:每房间独立 630ms 同步移动、冲突表迭代、箭头转向、吃宝石 feed/reverse、第 0 个反转特例照抄;静止也运行;步进后重算当前层光照。全图现状 1 只,实现按通用。

### 6.6 撤销(裁定 2/4 —— 差分、一次性、跨会话整局)

**空间账**

| 方案 | 每步 | 整局(2 万步) |
|---|---|---|
| 整幅快照 | ~4.6 KB | ~90 MB ❌ |
| **差分(采用)** | 典型 <200 B | **几 MB ✅** |

**模型(一次性,无 redo)**

- 状态序列 `S0 →E0→ S1 →E1→ … Sn`;条目 `Ei` 存 pre 侧差分与 pre 玩家状态;
- **差分只记录“玩家可影响”的格子**:rover 所在/移入的格子被过滤(裁定 6),避免整局历史混入 rover 轨迹;纯玩家移动仍入栈(玩家状态变化也算变更);
- **撤销不影响 rover**:撤销只回滚玩家侧差分与玩家状态;rover 位置/朝向/计时器与 `gems_stored` 保持当前值,rover 继续按 630ms 节拍自主循环移动;
- **commit()**:diff 非空 → 追加条目(顶部即最近);
- **undo()**:顶部非空 → 反向应用 top 的 diffs、恢复其 pre 状态,弹栈丢弃;重算光照;
- 撤销后执行新操作:与旧条目无冲突(历史仍为“自开局以来已应用条目”,继续追加)——语义:任意时刻可连续退格到 **S0(第一步之前)**;
- no-op 不产生条目;新游戏/checkpoint 恢复/读档替换整条历史(对应原 `flush_undo`);
- 内存软警戒(默认 64 MB 可调)超出时仅提示/压缩,不静默截断。

**跨会话(裁定 4)**

- 历史与当前状态**整体持久化到 IndexedDB**(`promesst2` 库):关浏览器再开 → 恢复 `{gamestate, checkpoint, history[]}` 后,仍可从当前点一路撤销回第一步;
- 写入策略:防抖(动作后 ~1s)+ `pagehide/beforeunload` 尽力冲刷;加载在进入游戏前完成(先出标题,读档完成后才可开局);
- 差分条目很小,IndexedDB 配额充裕;仍设“清理/导出”入口备查。

> 撤销多走了?没有重做 —— 把漏掉的几步重新操作一遍即可(裁定 2)。历史仍在,不会因误撤丢失已解部分:例如撤销了 5 步又走 2 步,世界状态即“从那之后重走”,旧条目保留,可继续撤回更早。

### 6.7 存档(IndexedDB)

- 库 `promesst2`,store `saves`,键 `v1.main`(多槽时 `v1.slot1..3`);
- 内容:`{meta, gamestate, checkpoint, history[]}`;
  - `history[]` = 自开局全部已应用差分条目(支撑撤销到第一步);
- 兜底:启动/加载失败 → 报错并在内存态运行(可继续游玩,提示本次不持久化);
- 通关标记写 meta;通关结算后清历史(新一周目从零开始);
- 旧 localStorage(如有)自动迁移一次。

## 14. 光束闪烁时钟说明(与 main.c 对齐)

原版 `main.c` 的主循环传入固定步长:

```c
stbwingraph_MainLoop(loopmode, 0.016f);
```

而 `loopmode()` 中:

- L2439: `animcycle += (uint)(dt * 1000);`   每帧 +16
- L2448: 游戏模式下 `animcycle += eff_time;`    再 +16

因此游戏内 `animcycle` 实际是 **每 16ms 逻辑帧 +32ms 动画时钟**。

网页版早期直接使用 `requestAnimationFrame` 的真实 `dt` 只累加一次 `animcycle`,会产生两个问题:

1. 闪烁速度约为原版游戏的一半;
2. 帧率波动和渲染限帧会改变 sin/取模突变的采样节奏,看起来忽快忽慢。

修复方式:

```js
const cycle = Math.floor(animcycle / 16) * 32;
```

再以 `cycle` 完全照抄 `main.c` L1860-1869 的闪烁公式。这样闪烁频率和节奏就与游戏模式下的原版 `animcycle` 对齐。
